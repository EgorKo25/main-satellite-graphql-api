# Разбор методов PostgreSQL и планов List

Исследован коммит `9dbbb3b75c29e8b8c0e8f1b1bb5548049760fd9c`. Рабочий код не изменён.

## Вывод

Большинство проверок в методах DB обосновано: это обработка ошибок операций и соблюдение контрактов транзакции. Основной обнаруженный риск производительности находится в плане `List`, а не в количестве `if`.

Предикат `($1::bigint IS NULL OR id = $1)` объединяет список и точечный поиск в одном подготовленном запросе. После серии глубоких страниц PostgreSQL **сам переключился на generic plan в режиме auto**. В этом плане поиск одного ID фильтрует практически весь Main вместо точечного Index Cond. Это воспроизведено и через SQL PREPARE, и через настоящий pgx с настройками по умолчанию.

Я бы следующим небольшим изменением разделил SQL-предикаты для списка и поиска по ID, сохранив одну общую проекцию и один метод List. Это одна осмысленная ветка выбора запроса, без новых слоёв и универсального построителя CRUD. Более узкий технический вариант — `pgx.QueryExecModeCacheDescribe` только для List; он тоже убирает найденную деградацию, но имеет стоимость повторного планирования/обработки SQL. Переписывать LATERAL и убирать проверки в том же изменении не требуется.

## Как проверено

- PostgreSQL 17.9 из существующей Dockertest-fixture, настоящие goose-миграции, отдельные БД. Windows/amd64, Docker Desktop, tmpfs; один последовательный клиент.
- Точный SQL List извлечён через Go AST из `internal/postgres/main.go`, а не переписан вручную.
- 100, 500 000 и 1 000 000 Main плюс столько же сателлитов суммарно. Типы распределены равномерно. Описания: 20% NULL, 20% пустых строк, 60% строк длиной 32 байта.
- Дополнительный миллион Main с 90% согласованно soft-deleted связок. После обновлений выполнялись VACUUM (ANALYZE) в собственной тестовой БД.
- Первая страница 20/100, последняя страница 100, последний существующий и отсутствующий ID.
- Текущий LATERAL, три обычных LEFT JOIN, обе формы с раздельным предикатом списка/ID; force_custom_plan и force_generic_plan. 160 комбинаций: один прогрев и пять EXPLAIN каждого случая, сохранены медианы и последний план. Ещё четыре случая проверяют auto после 12 глубоких страниц.
- Использован `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, SETTINGS, FORMAT JSON)`. TIMING OFF убирает замер времени каждого узла, но сохраняет общее Execution Time. Время EXPLAIN ниже — серверное, без передачи ответа клиенту и Go-декодирования.
- Дополнительный тест реального pgx измеряет wall time запроса и `pgx.RowToMap`: 10 повторов после прогрева, результаты сравниваются целиком. Это диагностическое сравнение режимов соединения, не бенчмарк HTTP API или рабочего collector.
- Альтернативные запросы возвращают одинаковые данные во всех проверенных здоровых наборах. Отдельно проверены 7 нарушений связности для текущего LATERAL и LEFT JOIN: неверный sub_id, неверный sub_obj, отсутствующий спутник, неверная обратная ссылка, удалённый спутник, лишний активный и лишний удалённый спутник. Оба запроса обнаруживают нарушения.

## 1. Кеш плана — приоритетная проблема

На миллионе активных Main:

| Поиск последнего ID | Execution Time, медиана | Обращения к shared buffers в сохранённом плане |
|---|---:|---:|
| Текущий SQL, custom plan | 0,043 мс | 14 hit |
| Текущий SQL, generic plan | 59,422 мс | 15 186 hit |
| Предикат `id = $1`, generic plan | 0,057 мс | 14 hit |

В плохом плане: `Gather Merge → parallel Index Scan main_active_id_idx`, условие ID находится в **Filter**, не в Index Cond. `Rows Removed by Filter = 333333`, `Actual Loops = 3`: суммарно отфильтрованы примерно 999 999 строк. Наличие слова Index Scan само по себе не означает точечный поиск.

В режиме auto после 12 глубоких страниц и одного запроса ID: `custom_plans = 5`, `generic_plans = 8`; последний поиск занял 60,709 мс. Такое же переключение наблюдалось на 500 000 Main и при 90% soft-deleted строк. Это не только искусственно принудительный generic plan.

Проверка через pgx, после 12 запросов `OFFSET 999900`, медианы wall time:

| Режим | Первая страница 100 | Последний ID | Отсутствующий ID | Последняя страница 100 |
|---|---:|---:|---:|---:|
| Текущий CacheStatement | 5,415 мс | 51,421 мс | 49,805 мс | 120,251 мс |
| Только CacheDescribe для List | 1,277 мс | 1,000 мс | 1,000 мс | 81,878 мс |
| Раздельные предикаты, CacheStatement | 1,122 мс | 0,528 мс | 0,509 мс | 82,827 мс |

У текущего CacheStatement после этой последовательности сервер продолжает использовать общий план. У раздельного запроса ID сервер тоже может выбрать общий план, но с прямым `id = $1` он остаётся точечным.

CacheDescribe не следует считать бесплатным ускорением. При прогреве обычной первой страницей, без смены на плохой общий план, первая страница 100 заняла 1,080 мс у CacheStatement и 1,473 мс у CacheDescribe. На поиск существующего ID: 0,568 и 0,516 мс соответственно. Это локальные диагностические замеры без статистического обещания такого коэффициента на другом стенде.

Минимальный технический вариант, пока только предложение:

```go
rows, err := db.pool.Query(ctx, query,
    pgx.QueryExecModeCacheDescribe, input.ID, input.Limit, input.Offset)
```

Он сохраняет описание типов в кеше клиента и не оставляет долгоживущий named prepared statement этого запроса. В отличие от QueryExecModeExec, здесь сохраняется возможность двоичного формата результатов. Проверены одинаковые значения nullable-полей, чисел и времени. Не нужно менять режим всего пула или добавлять SET LOCAL и транзакцию вокруг List.

Альтернатива, которую я предпочитаю по измеренному балансу: при nil ID — `WHERE deleted_at IS NULL`; при заданном ID — `WHERE deleted_at IS NULL AND id = $n`. Значения остаются параметрами, пагинация применяется после фильтра, обе формы остаются внутри одного GraphQL Query.main. Не надо дублировать весь большой SELECT ради двух предикатов.

Оговорка: разделение предикатов не гарантирует идеального плана для любых настроек сервера. Например, принудительный generic plan списка с неизвестными LIMIT/OFFSET в одном из вариантов выбрал параллельное полное чтение, сортировку и JIT. В штатном auto в проверенной последовательности раздельный список оставался на custom plan. Поэтому проверка именно фактического режима выполнения важнее рассуждения по тексту SQL.

## 2. LATERAL UNION ALL против трёх LEFT JOIN

На миллионе Main, первая страница 100, custom plan:

- Main: `Index Scan main_active_id_idx`, `Actual Rows = 100`.
- Каждый сателлит: `Index Scan *_main_id_key`, по 100 циклов.
- Всего 300 индексных обращений к сателлитам внутри одной SQL-команды, не N+1 сетевых запросов и не три полных сканирования больших таблиц.
- Ограничение страницы стоит до присоединения сателлитов.

Медианы серверного Execution Time:

| Main | Страница | LATERAL | LEFT JOIN |
|---:|---|---:|---:|
| 100 | первая 100 | 0,817 мс | 0,157 мс |
| 500 000 | первая 100 | 0,562 мс | 0,408 мс |
| 1 000 000 | первая 100 | 0,389 мс | 0,357 мс |
| 1 000 000 | последняя 100 | 94,620 мс | 94,501 мс |
| 1 000 000, 90% удалены | первая 100 | 0,365 мс | 0,365 мс |

На маленьких таблицах LATERAL выполняет короткие Seq Scan много раз; LEFT JOIN позволяет прочитать каждую маленькую таблицу один раз. На миллионе и короткой странице оба варианта используют те же индексы, по 1004 shared hit blocks. Это объясняет небольшой выигрыш альтернативы в этом случае.

Плоские JOIN не исправляют предикат с OR: с общим планом поиск ID остаётся дорогим. Проверка отсутствия других сателлитов в альтернативе сохранена. Просто присоединить только таблицу из sub_obj и забыть об остальных — изменение гарантий: UNIQUE(main_id) действует отдельно в каждой таблице и не запрещает одновременно Tool и Chair у одного Main.

## 3. Глубокий OFFSET и выбор сначала только ID

Текущий custom plan последней страницы миллиона активных Main читает 1 000 000 строк Main до выдачи 100. Сателлиты загружаются только для конечной страницы. Поэтому смена JSON/collector или удаление проверок в Go эту стоимость не устраняет.

Проверен вариант: CTE выбирает только ID страницы, затем JOIN main получает остальные поля по PK. Контракт LIMIT/OFFSET сохранён, индекс не добавлялся. Медианы EXPLAIN последней страницы 100:

| Состояние миллиона Main | Текущий запрос | Сначала ID |
|---|---:|---:|
| До ручного VACUUM | 95,569 мс | 154,507 мс |
| После VACUUM | 95,964 мс | 68,749 мс |
| 90% soft-deleted, после VACUUM | 52,543 мс | 8,579 мс |

На первой странице вариант с ID был медленнее: после VACUUM 0,362 → 0,487 мс. До VACUUM Index Only Scan всё ещё обращается к heap за проверкой видимости; после VACUUM Heap Fetches становятся нулевыми. Это не безусловная оптимизация.

В случае 90% удалённых текущий запрос выбирал parallel Seq Scan и сортировку, часть сортировки вышла во временный файл. Вариант с ID после VACUUM смог использовать существующий частичный индекс без загрузки полных строк для всего пропускаемого диапазона. Такая оптимизация полезна для определённого профиля данных, но не заменяет анализ частоты обновлений и VACUUM.

Keyset/cursor pagination решила бы саму необходимость проходить пропускаемые записи, но меняет текущий публичный контракт. В рамках этого анализа её не вводил.

## 4. Какие проверки оставить

Число if посчитано по текущему исходнику, включая defer/callback:

| Метод | if | Смысл |
|---|---:|---|
| Create | 8 | Возврат ошибок валидации входа, начала/записи/чтения/завершения транзакции и rollback |
| Update | 12 | 9 обработчиков ошибок, 2 правила состояния, 1 ветка title-only / satellite patch |
| Delete | 10 | 7 обработчиков ошибок, повторное удаление, 2 проверки RowsAffected |
| List | 5 | 4 обработчика ошибок, включая validator/collector, и проверка связности |

Это счёт if, не показатель cyclomatic complexity и не результат профилирования Go.

Сохранить:

- ошибки Begin/Query/Scan/Commit/Rollback: ошибка второй записи или commit не может давать успешный payload;
- проверку deleted_at после FOR UPDATE: от неё зависят NOT_FOUND/ALREADY_DELETED и корректность конкурентных операций;
- запрет смены разновидности сателлита;
- проверки отсутствующего/null/значения patch: nullable SDL не запрещает title:null и type:null самостоятельно;
- проверку связности и единственности сателлита: полиморфная связь целиком не обеспечена FK;
- RowsAffected, особенно сателлита: Exec не возвращает ошибку только потому, что UPDATE изменил ноль строк;
- фиксированный набор имён таблиц перед построением SQL.

Формально повторяющиеся места:

- проверка sub_obj в lockMain повторяет CHECK БД, но одновременно ограничивает имя таблицы перед динамическим SQL; удалять этот небольшой защитный барьер я не предлагаю;
- `main.deleted_at IS NULL` в UPDATE повторяет состояние уже заблокированной строки. Это защитный SQL-предикат, а не отдельный запрос или дорогая повторная валидация;
- ошибки Query и Collect обрабатываются отдельно, потому что отправка запроса и чтение/декодирование результата могут завершиться ошибками независимо.

Я не вижу здесь необходимости добавлять transaction runner, общий exactlyOne, цепочку DTO или дополнительные одноразовые хелперы. Они уменьшат видимый объём методов, но перенесут важные границы транзакции в другое место. Профиль CPU/heap приложения не снимался; обвинять validator или if в bottleneck по этому исследованию нельзя.

## Изменения после исследования

`List` исправлен: общий OR-предикат заменён выбором двух SQL-текстов с общей проекцией.
Параметры текущего запроса: limit `$1`, offset `$2`, при наличии ID — `$3`.
Регрессионный `TestListIDPlanAfterDeepPages` проверяет фактический SQL через EXPLAIN и бюджет буферов.
Числа выше относятся к исходному исследованию; `current.sql` сохраняет запрос до исправления.
Для воспроизводимости архивный harness теперь читает этот файл, а не изменяющийся исходник `main.go`.

После согласования с пользователем миграция 00002 перенесла согласованность пары в PostgreSQL.
Из lockMain удалён подсчёт сателлитов; из List — проверка `valid`. Ветки LATERAL теперь ограничены
`sub_obj`, поэтому исполняется только выбранная ветка. Исторические таблицы выше измеряют SQL
до этой миграции, а `migrated-million-plan.txt` — новый SQL на миллионе Main после её применения.
Результаты стоимости записи: `integrity-writes.txt`, `integrity-summary.txt`; методика и выводы — в README.

## Приоритет действий

1. Исправить зависимость List от общего плана универсального OR-предиката: раздельные предикаты либо локальный CacheDescribe. Добавить регрессионный сценарий «глубокие страницы → запрос ID на том же соединении».
2. Сохранить нынешние проверки и транзакции. Не менять схему/индексы без новой необходимости: нужные PK, UNIQUE(main_id), частичный индекс активных Main уже работают.
3. LEFT JOIN и CTE только с ID рассматривать отдельно, если профиль нагрузки оправдывает компромисс. По этим измерениям утверждать, что они всегда лучше, нельзя.

## Артефакты и воспроизведение

Проверка нового SQL после миграции на миллионе Main сохранена в `migrated-million-plan.txt`.
Исходник этой проверки — `migrated-million_test.go.txt`: тот же регрессионный тест, увеличенный
со 100 000 до 1 000 000 строк (соответственно изменены ID и OFFSET). Для повтора через overlay
используйте его как source, а `internal/postgres/integration_tests/list_plan_test.go` как target,
запустите `go test -overlay <overlay.json> -tags=integration ./internal/postgres/integration_tests
-run '^TestListIDPlanAfterDeepPages$' -count=1 -v -timeout=10m`. Исходные файлы не изменяются.
Это один диагностический EXPLAIN на существующий и отсутствующий ID: 8 и 3 shared hit blocks;
0,123 и 0,055 мс серверного Execution Time соответственно, без статистического сравнения времени.
У существующего ID два невыбранных индекса сателлитов имеют Actual Loops = 0.

- `plans.json`: 164 записи планов и измерений.
- `cache-modes.json`: 25 диагностических случаев pgx, времена и счётчики подготовленных планов.
- `late-materialization.json`: 18 сравнений обычной страницы и страницы только ID.
- `current.sql`, `joins.sql`, `ids-first.sql`: исследованные SQL.
- `analysis_test.go.txt`: исходник исследовательских тестов. Это текстовый артефакт; он не добавляет пакет или функции в приложение.

Из корня репозитория, PowerShell, при работающем Docker:

```powershell
New-Item -ItemType Directory -Force .tmp/explain-analysis | Out-Null
Copy-Item docs/analysis/2026-10-08-postgres/analysis_test.go.txt .tmp/explain-analysis/analysis_test.go
$root = (Get-Location).Path
$target = Join-Path $root 'internal/postgres/integration_tests/analysis_overlay_test.go'
$source = Join-Path $root '.tmp/explain-analysis/analysis_test.go'
$overlay = @{ Replace = @{ $target = $source } } | ConvertTo-Json
[IO.File]::WriteAllText((Join-Path $root '.tmp/explain-analysis/overlay.json'), $overlay)
go test -overlay .tmp/explain-analysis/overlay.json -tags=integration ./internal/postgres/integration_tests -run='^TestExplainAnalysis$' -v -count=1 -timeout=20m
go test -overlay .tmp/explain-analysis/overlay.json -tags=integration ./internal/postgres/integration_tests -run='^TestExplain(CacheModes|AlternativeIntegrity|LateMaterialization)$' -v -count=1 -timeout=10m
```

Overlay добавляет исследовательский test-файл только в сборку тестового пакета и использует существующие fixture/миграции. Для исторического сравнения harness откатывает 00002 только в своей временной БД и проверяет версию 1. Исходники проекта не подменяются. Результаты появляются в `.tmp/explain-analysis`; эту собственную временную папку после сохранения результатов можно удалить. Чужие БД/volumes не очищаются.

Все указанные исходные исследовательские сценарии завершились успешно. При подготовке harness исправлена ошибка перенумерации параметров в экспериментальном варианте без ID; это не ошибка рабочего SQL. В первоначальном исследовании рабочие Go-файлы, миграции и конфигурация не менялись; последующие изменения описаны отдельным разделом выше.

## Ограничения и первоисточники

Это последовательные локальные измерения с небольшим числом повторов и фиксированным порядком вариантов. Размер всей БД, свежесть статистики, visibility map, план кешированного запроса и параметры сервера меняют результат. Нет HTTP-нагрузки, p95/p99, конкуренции клиентов или измерений физического диска. Shared hit/read counts не следует складывать по всем узлам дерева: родитель включает работу потомков. Последний сохранённый план может иметь другое Execution Time, чем медиана пяти измерений.

- [EXPLAIN: BUFFERS, TIMING и границы измерения](https://github.com/postgres/postgres/blob/REL_17_STABLE/doc/src/sgml/ref/explain.sgml).
- [Index-only scans и visibility map](https://github.com/postgres/postgres/blob/REL_17_STABLE/doc/src/sgml/indices.sgml).
